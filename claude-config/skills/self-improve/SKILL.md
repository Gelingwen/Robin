# Self-Improve（Skill 自迭代）

## 核心原则

把"AI 记得"变成"文件里写着、工具能查、结果能验"。
- 优先解决真实问题，不追求复杂架构。
- 每次只改一小块；改之前先诊断，改之后要有证据。
- 没有证据，不写"验证通过"。

## 两种入口

| 情况 | 做什么 |
|---|---|
| 用户纠错 / 重复提同一条意见 | **记录反馈**（下面第 A 节），不要当场重写 Skill |
| 用户要求改进某个 Skill，或 feedback.md 攒了 ≥3 条未处理 | **改造 Skill**（下面第 B 节四步） |

## A. 记录反馈

追加一条到 `~/.claude/feedback.md` 的 `## Entries` 下，格式固定：

```markdown
### 2026-11-06 · <涉及的 skill 或 "global">
- 现象：用户说了什么 / 我做错了什么（一句话，引用原话）
- 原因：为什么会错（没规则 / 规则含糊 / 规则有但没执行）
- 改法：规则 | 样例 | 检查步骤 | 工具（选一个，写具体内容）
- 状态：未处理
```

记完告诉用户一句"已记到 feedback.md"。同一问题第二次出现时，直接进入 B。

## B. 改造 Skill（四步，一步一确认）

### 1. 诊断（只读，不改）

读目标 Skill、它引用的文件、以及它实际操作的对象（脚本、样例、历史输出，如果有）。用这四项写一份简短诊断（正文 ≤15 行）：

1. **工作地图**：目标、步骤、输入输出、依赖、关键分支
2. **工具化程度**：哪些步骤已经有命令/脚本；哪些是重复、确定性的但还靠文字描述
3. **验证机制**：现在怎么判断"做对了"？哪些只有文字说明，没有实际检查？
4. **反馈机制**：用户纠错后怎么改？feedback.md 里有哪些条目指向这个 Skill？

保留原有有效设计，不推倒重来。

### 2. 确认验收标准

在同一条消息里：先列出你从诊断推出的初步标准，再提问。每轮最多 3 个问题，只问文档和历史反馈里找不到具体答案的（feedback 只写了"改法：样例"而没给样例内容，仍算没答案）：

- 好结果长什么样？哪些要求必须满足，哪些只是偏好？
- 最不能接受什么错误？
- 哪些环节必须人工确认？哪些可以放心自动执行？

用户确认前不改文件。

### 3. 实施改造

按诊断结果，按需做，不是每项都要：

| 方向 | 做法 |
|---|---|
| 结构化 | 在 Skill 开头补一张简短的工作地图（目标 / 步骤 / 输入输出 / 验收点） |
| 工具化 | 重复、确定性的操作写成脚本放在 `scripts/`，Skill 里用 `bash scripts/x.sh` 调用；主观判断保留人工 |
| 可验证 | 明确的要求写成可运行检查；记录"检查了什么、结果、证据"；语义/审美类明确标注"需人工复核" |
| 可改进 | 把 feedback.md 里的条目转成：认可样例 > 检查步骤 > 规则。只改单次要求的，不写进长期规则，避免规则膨胀 |

处理过的 feedback 条目把"状态"改成"已处理 → <skill 路径>"。

### 4. 测试与交付

- 用 Skill 自带或 feedback 里的样例跑一遍对比：改前 vs 改后。
- 未经用户确认，不覆盖原文件：先写到 `SKILL.md.new` 或分支，确认后再替换。
- 交付说明只有四条：
  1. 改了什么，为什么
  2. 哪些问题现在可以自动检查
  3. 哪些问题仍需人工判断
  4. 下次用户提反馈时，怎么进入下一轮

每个改动标清状态：**自动验证通过 / AI 评估通过 / 人工确认通过 / 尚未验证**。

## 常见错误

| 错误 | 正确做法 |
|---|---|
| 用户一纠错就重写整个 Skill | 先记 feedback；同一问题出现第二次再改 |
| 把一次性要求写成永久规则 | 单次要求留在对话里；重复出现的才进 Skill |
| 不停加"注意：……"提示语 | 优先改成样例或检查步骤，提示语是最后手段 |
| 写"已验证"但没跑过 | 没跑就标"尚未验证" |
| 诊断阶段就开始改文件 | 第 1、2 步只读；用户确认后才动手 |
